# 内存与 CPU 实测结果

这份文档只写**实际测出来的数字**，不写估算值。每次改动如果影响资源占用，请重跑一遍并更新这里。

## 一、怎么测的

- 脚本：`.tools/screens/memstat.ps1`（单点测量）与 `.tools/screens/mem5.ps1`（五态自动测量）
- 归属判定：用 `Win32_Process` 查 `msedgewebview2.exe` 的命令行，只统计命令行里带 `ProjectFocusManager` 的那些，再递归把它们的子进程算进来。
  **不能直接 `Get-Process msedgewebview2` 数总数** —— 这台机器上别的软件（浏览器、编辑器）也在用 WebView2，会把数字算错。
- 内存口径：`WorkingSet64`（任务管理器里的「内存（工作集）」），单位 MB。
- CPU 口径：主进程 `TotalProcessorTime` 的累计值，单位秒。

## 三、五态实测（2026-11-01）

| 状态 | 主进程 | WebView2 进程数 | WebView2 占用 | 合计 | 主进程累计 CPU |
|---|---:|---:|---:|---:|---:|
| 刚启动、停在专注页 | 146.8 MB | 0 | 0 MB | **146.8 MB** | 3.0 s |
| 正在专注计时 | 153.8 MB | 0 | 0 MB | **153.8 MB** | 5.6 s |
| 打开内置 ChatGPT 后 | 161.0 MB | 6 | 437.9 MB | **598.9 MB** | 6.5 s |
| 点「关闭网页」后 | 161.3 MB | **0** | **0 MB** | **161.3 MB** | 6.7 s |
| 关窗口隐藏到托盘待机 | 161.5 MB | 0 | 0 MB | **161.5 MB** | 9.2 s |

## 四、从这组数字能确认的事

1. **启动不加载网页内核**：启动态 WebView2 进程数是 0，符合「只有用户主动打开才初始化」的要求。
2. **关掉网页后内核真的退出了**：从 6 个进程、437.9 MB 变成 0 个进程、0 MB。
   这一点原本没把握（WebView2 运行时有权自己决定何时回收），是实测确认的。
   同时 `data\WebView2\EBWebView` 目录（约 18 MB）保留下来，登录状态不会丢。
3. **离开页面也会释放**：从「内置 ChatGPT」切回「专注」时同样会关掉网页，进程数归零。
4. **托盘待机不额外占内存**：隐藏窗口后没有多出来的进程，CPU 也没有持续增长
   （9.2 s 里包含脚本连续点击、开网页、关网页的操作时间）。

## 五、Release 五态实测（2026-11-01）

同一台机器，`dotnet build -c Release`，数据目录 `bin\Release\net10.0-windows\data`（全新库，UIA 造了一个测试项目）。跑了两遍取一致性：

| 状态 | 第一遍 | 第二遍 |
|---|---:|---:|
| 刚启动、停在专注页 | 144.7 MB | 160.8 MB |
| 正在专注计时 | 157.6 MB | 160.7 MB |
| 打开内置 ChatGPT 后（WebView2 6 进程 ≈445 MB） | 611.9 MB | 605.1 MB |
| 点「关闭网页」后（关后 4 秒测） | 477.8 MB | 463.1 MB |
| 关窗口隐藏到托盘待机（WebView2 已 0 进程） | 163.3 MB | 170.1 MB |

### Release 与 Debug 的结论对比

1. **Release 主进程没有明显下降**（145–170 MB vs Debug 147–162 MB）。
   Debug 未优化不是主因——大头是 WPF 基线 + 四页常驻 + WebView2 宿主。「< 60 MB」的目标以当前架构达不到，如实放弃；对一台日常桌面工具，170 MB 待机可接受，不再为它做架构级优化。
2. **「关网页后内核退出」在 Release 上依然成立，但有约 8–10 秒延迟**。
   专项探针 `.tools/screens/webview-teardown.ps1`：关闭网页后每 2 秒测一次，
   t+2s～t+6s 仍是 5 进程 ≈291 MB，**t+8s 归零**（从点击关闭算约 10 秒）。
   M4 测量点固定在关后 4 秒，正好撞在回收窗口里；最终一定退出，只是 WebView2 运行时自己决定何时收。
3. **启动不加载网页内核、托盘待机不额外占内存**这两条在 Release 上复验通过。

| 检查项 | 结果 |

| Release exe 二进制内嵌该清单 | ✅（直接在 exe 里 grep 到 PerMonitorV2） |

| 多显示器 / 非 100% 缩放下的实测 | ⚠️ 本机只有一个显示器且固定 100% 缩放，未测；清单已按 PerMonitorV2 声明，WPF 自带该模式支持 |

核验脚本：`.tools/screens/dpicheck.ps1`（改系统缩放后重跑即可得真实多缩放数据）。

## 七、还没达到的地方（如实记录）

1. **打开网页时 ≈445 MB 是 Chromium 内核的固有开销**，不是本程序的代码造成的；
   能做的只有「不用的时候关掉」，这一点已经做到（含约 10 秒延迟回收）。
2. **多显示器、非 100% 缩放**下的高 DPI 表现未实测（见第六节）。
3. 本机 `C:\Users\<用户>\AppData\Local` 有 ACL 限制，测量时数据落在 `bin\...\data`；
   正式版使用 `%LOCALAPPDATA%\ProjectFocusManager`，路径不同不影响上述结论，但打包后要复测一次。

## 八、怎么复现

```bash
# 1) 编译并启动（先确保没有旧实例在跑）
powershell -NoProfile -Command "Get-Process -Name ProjectFocusManager -ErrorAction SilentlyContinue | Stop-Process -Force"
cd /d/focustool && source build/env.sh && dotnet build FocusManager.slnx -c Debug
cmd //c start "" "D:\focustool\src\FocusManager.App\bin\Debug\net10.0-windows\ProjectFocusManager.exe"

# 2) 五态自动测量（会自己开始专注、开网页、关网页、最小化到托盘）
powershell -NoProfile -ExecutionPolicy Bypass -File .tools/screens/mem5.ps1 -ProcId <pid>

# 3) 或者只测当前状态
powershell -NoProfile -ExecutionPolicy Bypass -File .tools/screens/memstat.ps1 -MainPid <pid>
```
